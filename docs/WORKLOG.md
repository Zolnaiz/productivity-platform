# Хийсэн ажлын тэмдэглэл

Энэ файлд Claude Code-ийн cloud session-д хийсэн ажлыг товч тэмдэглэв. Тоонууд бүгд бодит ажиллуулсан тестээс авсан. Дэлгэрэнгүй үр дүн [RESULTS.md](RESULTS.md)-д бий.

## PR #7 (main-д нийлсэн): 5 үе шат

1. **Бүртгэлийн амьдралын мөчлөг.** Нууц үг сэргээх (forgot/reset, токеныг нэг удаа, атомаар хэрэглэнэ; бүртгэл байгаа эсэхийг хариуны хугацаагаар задруулахгүй), урилга хүлээн авах, CSV/Excel-ээс олноор урих, санал хүсэлтийн хуудас, өөрийн бүртгэлийн хуудас.
2. **UI хялбаршуулалт.** Цэсийг түвшинд хувааж «Бусад» хэсэг нэмсэн, мобайлд «Өнөөдөр» таб, 5S бүсийн хүснэгт, ерөнхий (компанийн нэргүй) 5S заавар, загварын сан, тусламжийн хуудас.
3. **K2/K4/K6 хэмжүүр.** `monthly-measurements.ts` (хувилбар 2): хоцорсон ажил, 5S засварын хаалтын хугацаа, долоо хоногийн тайлангийн хувь. Нотлох бичлэгүүд тайлан болон CSV-д гарна. Тайлбар: [measurements.md](measurements.md).
4. **Хүлээн авах тест ба benchmark.** UC-01…UC-22-ын тест (`npm run test:uc`), `npm run results` → RESULTS.md, `npm run bench`. Benchmark-аар сарын тайлангийн p95 1753 мс байсныг Intl.DateTimeFormat-ыг кэшлэж 185 мс болгосон.
5. **Баримт бичиг.** ISO 25010 хураангуй, README, [DEPLOY.md](DEPLOY.md).

Тестээр олдож засагдсан алдаа: үл мэдэгдэх 5S загвараар аудит эхлүүлэхэд 500 буцдаг байсныг 404 болгосон; axe-ийн контрастын хоёр алдаа; migration-ий нэр glob-д таарахгүй байсан.

## PR #8 (`feat/next-improvements`, нийлүүлэхийг хүлээж буй)

- **PDCA «Check».** Аудитаас үүссэн засвар тухайн бүсийн дараагийн аудитаар сайжирсан эсэхийг шалгана (`GET /operations/improvement-verification`, вэб: 5S → Үр дүн).
- **Хувийн тэмдэглэл серверт.** `personal_notes` хүснэгт; хөтөч дээрх хуучин тэмдэглэлийг нэг удаа серверт шилжүүлнэ; устгах товч.
- **Төвлөрлийн session ба тэмдэг (badge).** `focus_sessions` хүснэгт; 5 тэмдгийг хэрэглэгчийн өөрийн бичлэгээс тооцно.
- **Байгууллагын тохиргоо алга болдог алдаа (lost update).** Сервер `settings`-ийг бүхэлд нь сольдог байсан тул нэг түлхүүрийг хадгалахад бусад нь дарагдаж болдог байв. Одоо түлхүүр тус бүрээр нийлүүлнэ. Live e2e тест «workspace setting saved…» үе үе унадаг байсны шалтгаан нь энэ байсан.
- **Вэбийн эхний ачаалал багассан (аудит №18).** Нүүр болон нэвтрэх хуудаснаас бусад бүх хуудас хэрэглэгч анх нээх үед ачаалагдана. Мөн график номын сан React-ийг өөртөө татаж, эхний ачаалалд орж байсныг зассан. Эхний ачааллын JS 1541 kB → 642 kB (gzip 417 → 201 kB), `vite build`-ээр хэмжсэн.
- **Өглөөний хурлын эрт анхааруулга (аудитын санаа №5).** «Анхаарах» хэсэгт 2 хоногийн дотор дуусах ёстой ч эхлээгүй ажлын тоо, жагсаалт нэмэгдсэн. «Багаас гарсан» хэсэгт энэ долоо хоногт тайлангаа бичээгүй хүмүүсийн нэрс гарна. Тайлан бичих ёстой хүмүүсийг K6-тай ижил тодорхойлсон: идэвхтэй ажилтан ба менежер.
- **Хаасан сарыг дахин нээх нь шалтгаантай, түүхтэй болсон (аудитын санаа №6).** Дахин нээхэд шалтгаан (3–500 тэмдэгт) заавал бичнэ. Хэн, хэзээ, яагаад нээснийг хаасан хувилбарын хамт хадгална (migration 1781265200000). Сарын тайлангийн хуудсанд «Энэ тайлангийн өмнөх хувилбарууд» карт гарч, хувилбар бүрийн K1–K6, дууссан ажил, цагийг одоогийн дүнтэй харьцуулна. Өөрчлөгдсөн дүнг тодруулна. API өөрчлөгдсөн: `DELETE /operations/monthly-closes/:month`-ын оронд `POST /operations/monthly-closes/:month/reopen` `{reason}` болсон. Шинэ нь `GET /operations/monthly-closes/:month/history`. Аудитын бүртгэлд «reopen» үйлдэл warning түвшинтэй бичигдэнэ.
- **Offline давталтыг сервер дээр idempotent болгосон (execution plan-ийн дараагийн ажил №3).** `Idempotency-Key` толгойтой POST хүсэлтийг тухайн хэрэглэгчид 24 цаг хадгалдаг болсон (`idempotency_keys` хүснэгт, migration 1781265300000). Нэг түлхүүрээр дахин ирсэн хүсэлтийг дахин бичихгүй, анхны хариуг `Idempotent-Replayed: true` толгойтой буцаана. Анхны хүсэлт дуусаагүй байхад ирсэн хуулбар 409 `REQUEST_IN_PROGRESS` авна. Өөр хүсэлтэд ашигласан түлхүүр 409 `IDEMPOTENCY_KEY_REUSED` авна. Давтан хүсэлт аудитын бүртгэлд дахин орохгүй (бодит Postgres дээр шалгасан). Flutter-ийн outbox хадгалсан өөрчлөлт бүрд түлхүүр өгнө. Өдрийн ажлын бүртгэл анхны илгээлтээсээ эхлээд түлхүүртэй явдаг болсон тул хариу нь timeout болсон бичлэгийг ч outbox-д хадгалж, давхардуулахгүйгээр дахин илгээнэ. Өмнө нь ийм бичлэг алдагддаг байсан.
- **Засварын гогцоо бүрэн болсон (execution plan-ийн дараагийн ажил №2).** Аудитаас үүссэн засварт «үндсэн шалтгаан» талбар нэмсэн. Засварыг хариуцсан ажилтан өөрөө бичиж болно. Менежер дууссан засварыг баталгаажуулна (`POST /tasks/:id/sign-off`, `fixes:signoff` эрх). Өөрийнхөө засварыг баталгаажуулж болохгүй. Засварыг дахин нээвэл баталгаажуулалт цуцлагдана. Энгийн засах хүсэлтээр баталгаажуулалтыг бичиж болохгүй. «Засварын баталгаажуулалт» картад үндсэн шалтгаан, хэн хэзээ баталгаажуулсан нь харагдана (migration 1781265400000). Мөн өмнөх алдааг зассан: картад засварын нэр англиар гардаг байсан, одоо уншигчийн хэлээр гарна.
- **Вэбийн refresh токен HttpOnly cookie-д шилжсэн (roadmap №4-ийн эхний алхам).** Өмнө нь 7 хоног хүчинтэй refresh токен localStorage-д байсан тул XSS script түүнийг хулгайлж session-ийг долоо хоног барьж чадахаар байв. Одоо `pp_refresh` cookie (HttpOnly, SameSite=Strict, Path=/api/auth, production-д Secure) болсон. Script хамгийн ихдээ 1 цагийн хандалтын токеныг л авч чадна. Mobile өөрчлөгдөөгүй, cookie горим нь `X-Session-Cookie` header-ээр асдаг. Өмнө нь нэвтэрсэн хөтөч хуучин токеноо нэг удаа cookie болгон солиулж, хадгалсан хуулбараа устгана. Вэбийн `VITE_API_URL`-ийн анхны утга `/api` (ижил origin) болсон. Үлдсэн ажил: хандалтын токен localStorage-д хэвээр байна. Мөн серверт refresh токен цуцлах (logout, нууц үг солих үед) механизм алга.
- **Нууц үг солих эсвэл сэргээхэд бусад бүх session дуусна.** Хэрэглэгчид `token_version` нэмсэн (migration 1781265500000). Refresh токен үүсэхдээ тухайн хувилбарыг агуулна. Нууц үг солих эсвэл сэргээх үед хувилбар нэмэгдэж, өмнөх бүх refresh токен 401 авна. Нууц үгээ сольсон төхөөрөмж хариундаа шинэ session авч, нэвтэрсэн хэвээр үлдэнэ: вэб шинэ cookie, mobile шинэ токен хадгална. Хандалтын токен (1 цаг) хүчинтэй хэвээр үлдэнэ.
