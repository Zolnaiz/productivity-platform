## 6. Демо сценари

Бэлтгэл: Docker Desktop асаалттай байх ёстой. Демо өгөгдөлтэй `pp_demo` сангаар ажиллуулахдаа API-г PowerShell-ээр ингэж асаана:

```
cd backend; $env:DB_DATABASE = 'pp_demo'; npm run start:dev
```

Вэбийг `admin-web` дотор `npm run dev -- --host 127.0.0.1 --port 3001`-ээр асаана. Нэвтрэх бүртгэлүүд seed-ийнх: `owner@example.com` (админ), `operator@example.com` (ажилтан), нууц үг `Password123`. Өөрийн dev сангаар бол `scripts/start-dev.ps1`-ийг ашиглана.

1. **Ажил оноох → утаснаас дуусгах** (UC-09, UC-01). Менежер вэбээс ажил үүсгэж ажилтанд оноох. Ажилтны утсанд мэдэгдэл ирж, ажлаа дуусгана.
2. **5S аудит, сүлжээгүй үед** (UC-08, UC-02). Утсыг онгоцны горимд оруулж бүсийн шалгах хуудсыг бөглөх, оноо 85-аас доош байлгах. «Илгээхийг хүлээж буй» тоо харагдана. Сүлжээг асаахад илгээгдэж, бүсийн хариуцагчид засах ажил үүснэ.
3. **Засвар → шалтгаан → баталгаажуулалт** (UC-14). Засах ажлыг дуусгаж үндсэн шалтгааныг бичих. Менежер баталгаажуулна. Бүсийг дахин аудитлаж 85-аас дээш оноо авахад 5S → Үр дүн хэсэгт засвар «verified» болно.
4. **Сарын тайлан** (UC-16). K1–K6 болон тэдгээрийн нотлох бичлэгийг үзүүлэх. Өмнөх сарыг хаах, дараа нь шалтгаантай дахин нээж түүхийг харуулах.

Сүлжээ эсвэл төхөөрөмж ажиллахгүй бол урьдчилан бичсэн бичлэгээр үзүүлнэ.

### Нийтэд нээх (жинхэнэ утаснаас демо хийх)

Production стек компьютер дээр ажиллаж, Cloudflare Tunnel-ээр HTTPS хаягтай болно. Сервер түрээслэх, порт нээх шаардлагагүй.

**Компьютер дахин асаасны дараа нэг командаар бүгдийг сэргээнэ:**
```
powershell -ExecutionPolicy Bypass -File scripts\start-public.ps1
```
**Автоматаар:** «Productivity Platform - public start» ажил энэ скриптийг Windows-д нэвтэрснээс 1 минутын дараа, мөн 15 минут тутам ажиллуулна.
- Ажил тунелийг эзэмшиж, 5 минут тутам шалгана.
- Тунел зогсох эсвэл 15 минут хариу өгөхгүй бол дараагийн ажиллагаа шинэ тунел асаана. Энэ нь компьютер унтах эсвэл сүлжээ тасрахад хэрэгтэй.
- Хаяг ажиллаж байх хооронд өөрчлөгдөхгүй.
- Шинэ хаяг гарахад цонх харуулна (10 минутын дараа өөрөө хаагдана). Хаяг `public-url.txt`-д, лог `%TEMP%\productivity-start-public.log`-д бичигдэнэ. Унтраах бол: `Unregister-ScheduledTask -TaskName 'Productivity Platform - public start'`.

Скрипт дараах алхмуудыг хийгээд эцэст нь нийтийн хаягийг хэвлэнэ: Docker асаах, stack болон нөөцлөлтийг асаах, HTTP/2 тунел асаах, шинэ хаягийг `.env.production`-д бичих, backend-ийг дахин асааж интернэтээр шалгах. Утасны аппыг дахин build хийх шаардлагагүй: нэвтрэх дэлгэц дээр «Сервер → Солих»-оор шинэ хаягийг оруулна.

Доорх нь скриптийн хийдэг алхмууд, гараар хийх тохиолдолд:

1. Стекийг асаах (Docker Desktop асаалттай):
   ```
   docker compose --env-file .env.production -f docker-compose.prod.yml -p productivity-prod up -d --wait
   ```
2. Тунел асаах. Гарсан `https://….trycloudflare.com` хаягийг тэмдэглэнэ:
   ```
   & 'C:\Program Files (x86)\cloudflared\cloudflared.exe' tunnel --no-autoupdate --protocol http2 --url http://localhost:3101
   ```
3. Хаяг өөрчлөгдсөн бол `.env.production`-ийн `APP_BASE_URL`, `CORS_ORIGINS`-ийг шинэ хаягаар сольж backend-ийг дахин асаана (1-р алхмын тушаалын төгсгөлд `backend` гэж нэмнэ).
4. Апп: `mobile-flutter` дотор
   ```
   flutter build apk --release --flavor production --dart-define=API_BASE_URL=<хаяг>/api
   ```
   Гарсан `build/app/outputs/flutter-apk/app-production-release.apk`-г утсанд суулгана. Хаяг өөрчлөгдвөл APK-г дахин build хийх шаардлагагүй: нэвтрэх дэлгэц дээр «Сервер → Солих»-оор шинэ хаягийг оруулна.
5. Production сан хоосон тул эхлээд `<хаяг>/register` хуудсаар байгууллага, админ бүртгэл үүсгэж, ажилтнуудаа вэбээс урина.

Quick tunnel-ийн хаяг cloudflared-ийг дахин асаах бүрт өөрчлөгдөнө. Пилот туршилтад тогтмол хаяг (нэрлэсэн tunnel эсвэл өөрийн домэйн) хэрэгтэй.

## 7. Гарч болох асуулт

- **«O(n)» гэдэгт n нь юу вэ?** Аудитын оноонд шалгах хуудасны асуултын тоо. K1–K6-д ажил, аудит, тайлангийн бичлэгийн тоо. K6 нь хүн × долоо хоногоор тооцогдоно (O(p·w)). PDCA-д аудитуудыг бүсээр эрэмбэлэх нь O(r log r).
- **10 000 бүртгэл бодит ачааллыг төлөөлөх үү?** 50 хүн өдөрт нэг бүртгэл хөтөлбөл 4 000 бүртгэл нь ойролцоогоор 4 сарын өгөгдөл. Хязгаарлалт: клиент, сервер нэг машин дээр байсан, хүсэлтүүд дараалсан. Зэрэг олон хэрэглэгчийн ачаалал, бодит сүлжээг хэмжээгүй, үүнийг III үзлэгт хийнэ.
- **Сарын тайлан яагаад 1.75 секунд байсан бэ?** Огноог цагийн бүсээр хөрвүүлэх функц дуудагдах бүртээ шинэ `Intl.DateTimeFormat` үүсгэдэг байсан. Алгоритм O(n) хэвээр байсан ч нэг алхмын өртөг өндөр байв. Formatter-ийг кэшлэхэд 9 дахин хурдассан (14-р слайд).
- **K1 яагаад зөвхөн дууссан ажлаас тооцогддог вэ?** Дуусаагүй хоцорсон ажлыг K2 хэмждэг, ингэж хоёр үзүүлэлт давхардахгүй. Дипломын томьёо өөр байгааг 3-р хэсгийн 2-р зүйлд заасан. Үзлэгээс өмнө тааруулах.
- **Клиент оноог хуурамчаар илгээж болох уу?** Үгүй. Вэб, утас оноог бөглөх явцад харуулдаг ч засах ажлын шийдвэр гаргаж, K3-т тоологдох оноог сервер хариултаас дахин тооцдог (`scoreFromAnswers`). Клиентийн илгээсэн оноог зөвхөн тооцох асуултгүй шалгах хуудсанд хадгална. UC-08-ийн тест үүнийг шалгадаг: 100 гэж илгээсэн ч хариулт нь 20 оноо л өгөх аудит 20 оноотой хадгалагдаж, засах ажил үүснэ.
- **Idempotency-Key яагаад 24 цаг?** Кодонд `IDEMPOTENCY_TTL_MS` гэж тогтоосон, үндэслэл нь баримтжаагүй. Тайлбарлах бол: дахин илгээлт сүлжээ сэргэхэд эсвэл апп нээгдэхэд хийгддэг тул ихэнх нь нэг өдрийн дотор болно. Хугацаа нь дууссан түлхүүрийн хүсэлт шинэ бичилт болно. Түлхүүр хэрэглэгч бүрт тусдаа тул бусдын хариуг таах боломжгүй.
- **Хариу нь замдаа тасарсан бичилт давхардах уу?** Үгүй. Утас хүсэлт серверт хүрсэн эсэхийг ялгаж чадахгүй тул бичилт бүр анхны илгээлтээсээ `Idempotency-Key`-тэй явж, хариу ирээгүй бол тэр түлхүүрээрээ хадгалагдана. Дахин ирэхэд сервер анхны хариугаа буцаана. Үүнийг жинхэнэ сервертэй холболт тасалдаг тест шалгадаг; уг тест өмнө нь санаа, аудит хоёр удаа бичигддэгийг илрүүлсэн (11.14).
- **Хоёр утас офлайнаар нэг зүйлийг өөрчилбөл?** Outbox ихэнхдээ шинэ бичлэг үүсгэдэг (POST: аудит, бүртгэл, санаа, Gemba). Ажлын төлвийг PATCH-аар, долоо хоногийн тайланг PUT-аар илгээдэг тул тэдгээрт сүүлд ирсэн нь үлдэнэ. Ерөнхий зөрчил шийдэх механизм байхгүй, энэ нь цаашдын ажил. Харин байгууллагын тохиргоог түлхүүр тус бүрээр нийлүүлдэг болсон.
- **Тестийн хамрах хувь (coverage) хэд вэ?** Хэмжээгүй (`npm run test:cov` боломжтой). Хамрах хүрээг use-case-ээр баталгаажуулсан: 22 use-case бүр үндсэн ба өөр урсгалтай. Шаардлагад хэрэгтэй бол үзлэгээс өмнө нэг удаа ажиллуулж тоог бэлдэх.
- **SUS яагаад алга?** SUS-ийг бодит хэрэглэгчид системийг хэрэглэсний дараа бөглөдөг. Пилотын (2 + 4 долоо хоног) төгсгөлд авна. Автомат хүртээмжийн шалгалт (axe, WCAG 2.1 AA) одоо ч хийгддэг.
- **AI ашигласан уу?** Хоёр газар хариулт бэлдэх:
  - Систем дотор: сарын тоймын ноорог. Зөвхөн нэргүй, нэгдсэн тоо явна, менежер батална.
  - Хөгжүүлэлтэд: хэрэв хэрэгсэл ашигласан бол юуг өөрөө шийдсэн, юуг хэрэгслээр хийлгэсэн, хэрхэн шалгасныг үнэнээр хэлэх. Слайд бүрийн кодыг өөрөө тайлбарлаж чаддаг байх.
