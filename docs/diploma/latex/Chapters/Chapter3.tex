\subsection{Аудитын оноо тооцох ба засах ажил үүсгэх}
Шалгах хуудасны асуулт оноо (0..maxScore, анхдагч 5), тийм/үгүй, текст гэсэн гурван төрөлтэй. Текст хариулт нотолгоо тул оноонд тооцогдохгүй; хариулаагүй онооны асуулт 0 гэж тооцогдоно, учир нь шалгаагүй зүйлийг тэнцсэн гэж үзэх боломжгүй. Оноо нь
\begin{equation}
S = \mathrm{round}\left(\frac{\sum_{q} e_q}{\sum_{q} m_q} \times 100\right)
\end{equation}
энд $e_q$ -- асуултын авсан оноо, $m_q$ -- боломжит дээд оноо. Оноо 85\%-иас доош бол бүсийн хариуцагчид 7 хоногийн хугацаатай засах ажил үүсэх ба 70\%-иас доош бол өндөр ач холбогдолтой болно (Эх код~\ref{lst:audit}).

\begin{lstlisting}[caption={Аудитын оноо ба засах ажил},label={lst:audit}]
function scoreAnswers(template, answers):
    earned = 0; possible = 0
    for q in template.questions:
        if q.type == "score":  possible += q.maxScore or 5; earned += answers[q.id] or 0
        if q.type == "yes_no": possible += 1; earned += (answers[q.id] == "yes") ? 1 : 0
    return possible > 0 ? round(earned / possible * 100) : 0

function correctiveWork(run):
    if run.status == "draft" or run.score >= 85: return null
    zone = zoneOf(run)
    return createTask(title = "5S follow-up: " + zone.name,
                      assignee = zone.owner, due = today + 7 days,
                      priority = run.score < 70 ? high : medium,
                      source = (audit_run, run.id))   // one task per run
\end{lstlisting}

Алгоритмын хугацааны төвөгшил асуултын тоо $n$-ээр $O(n)$. createTask нь (sourceType, sourceId) хосоор тухайн эх сурвалжаас үүссэн нээлттэй ажил байгаа эсэхийг шалгадаг тул нэг аудитыг дахин илгээхэд ажил давхардахгүй.

\subsection{Сүлжээгүй горимын дараалал (outbox)}
5S аудит хийгддэг агуулах, цех, подвал зэрэг газарт сүлжээ тасалдах нь элбэг. Гар утасны апп илгээж чадаагүй бичилтийг хийсэн дарааллаар нь утасны санах ойд хадгалж, сүлжээ сэргэх, апп дахин нээгдэх эсвэл хэрэглэгч ``Одоо илгээх'' дарах үед илгээнэ (Зураг~\ref{fig:outbox}). Гол асуудал нь давхар бүртгэл: хариу ирээгүй хүсэлт серверт хүрч бичигдсэн байж болно. Эхний хувилбарт зөвхөн серверт огт хүрээгүй нь тодорхой (холболт тогтоогдоогүй) хүсэлтийг дараалалд хийж, timeout-ыг дахин илгээдэггүй байв. Ингэхэд хариу нь алдагдсан өдрийн бүртгэл утсанд алга болдгийг тест илрүүлсэн тул дараалалд хадгалах өөрчлөлт бүрд түлхүүр өгч, сервер нэг түлхүүрээр нэг л удаа бичдэг болгов (\ref{sec:idempotency}-р хэсэг). Өдрийн бүртгэл анхны илгээлтээсээ түлхүүртэй явдаг тул хариу ирээгүй бүх тохиолдолд (холболтгүй, timeout) хадгалагдана; бусад бичилт холболтгүй үед хадгалагдаж, хадгалагдахдаа түлхүүр авна. Дарааллыг илгээх үед сервер 4xx хариугаар татгалзвал тэр бичилтийг хасч хэрэглэгчид мэдэгдэнэ; сервер алдаатай (5xx), нэвтрэлт дууссан (401) эсвэл ижил түлхүүртэй анхны хүсэлт боловсруулагдаж байгаа бол хадгалаад дараа дахин оролдоно (Эх код~\ref{lst:outbox}).

\begin{figure}[H]
\centering
\includegraphics[width=0.9\linewidth]{Figures/outbox.png}
\caption{Сүлжээгүй горимын дарааллын урсгал}
\label{fig:outbox}
\end{figure}

\begin{lstlisting}[caption={Outbox дараалал},label={lst:outbox}]
function save(write):                       // a daily log carries its key from the first send
    try: api.send(write, idempotencyKey = write.key)
    catch error:
        if neverSent(error) or (write.key and unanswered(error)):
            outbox.append(write with key = write.key or newKey())
        else: throw error                   // 4xx, 5xx: shown to the person

function flush():                           // network back / app opened / "send now"
    for write in outbox (in order):
        try: api.send(write, idempotencyKey = write.key); outbox.remove(write)
        catch error:
            if no response or status >= 500 or status == 401
               or error.code == REQUEST_IN_PROGRESS: break   // retry later
            outbox.remove(write); refused += 1               // 4xx: final answer
\end{lstlisting}

Унших тал нь мөн адил хамгаалагдсан. Утас ажил, 5S талбай ба шалгах хуудас, санаа, мэдэгдэл, өдрийн бүртгэлийг серверээс амжилттай уншсан бүртээ санах ойдоо хадгална (readThrough). Дараагийн уншилт сүлжээгүйн улмаас (холболтгүй эсвэл хариу ирээгүй) бүтэлгүйтвэл хадгалсан хувилбарыг харуулж, дэлгэцийн дээд хэсэгт хэдэн цагт уншсаныг заана, ингэснээр хэрэглэгч хуучин мэдээллийг одоогийн гэж андуурахгүй. Сервер татгалзсан (жишээ нь 401) бол хуучин өгөгдлөөр нуухгүй. Нэг утсыг ээлжээр хэрэглэж болох тул зөвхөн тухайн хүний өөрийн ажлыг хадгалж, хэрэглэгч гарах, session дуусах эсвэл шинээр нэвтрэхэд санах ойг цэвэрлэнэ. Зураг хавсаргахад л сүлжээ шаардлагатай хэвээр.

\subsection{Давхар бичилтээс сэргийлэх (Idempotency-Key)}
\label{sec:idempotency}
Клиент бичих (POST) хүсэлтдээ \texttt{Idempotency-Key} толгой хавсаргавал сервер (хэрэглэгч, түлхүүр) хосыг \texttt{idempotency\_keys} хүснэгтийн давтагдашгүй индексээр эзэлнэ (Зураг~\ref{fig:idempotency}). Эхний хүсэлт бичилтээ хийж, хариугаа түлхүүрийн хамт хадгална. Ижил түлхүүрээр дахин ирсэн хүсэлт шинээр бичигдэхгүй, анхны хариугаа \texttt{Idempotent-Replayed: true} толгойтой авна. Анхны хүсэлт дуусаагүй байхад ирсэн хуулбар 409 (REQUEST\_IN\_PROGRESS), өөр хүсэлтэд ашигласан түлхүүр 409 (IDEMPOTENCY\_KEY\_REUSED) хариу авна. Амжилтгүй болсон хүсэлт түлхүүрээ суллаж, дахин оролдох боломж үлдээнэ (Эх код~\ref{lst:idempotency}). Түлхүүр 24 цаг хадгалагдаж, дараа нь цагийн хуваариар устгагдана. Түлхүүр хэрэглэгч бүрт тусдаа тул бусдын хариуг таах боломжгүй, давтагдсан хүсэлт үйл ажиллагааны түүхэнд дахин бичигдэхгүй. Ингэснээр NFR-05-ийн ``давхар илгээлтээс сэргийлнэ'' шаардлага сервер талдаа баталгаажна.

\begin{figure}[H]
\centering
\includegraphics[width=0.95\linewidth]{Figures/idempotency.png}
\caption{Хариугаа алдсан бичилтийг ижил түлхүүрээр дахин илгээх}
\label{fig:idempotency}
\end{figure}

\begin{lstlisting}[caption={Idempotency-Key-ийг эзлэх},label={lst:idempotency}]
function intercept(request):
    if request.method != POST or no request.key: return handle(request)
    claim = claimKey(user, request.key, "POST " + request.path)
    if claim.replay: return claim.response with header Idempotent-Replayed: true
    try: response = handle(request); complete(claim, response); return response
    catch error: release(claim); throw error            // a failed write keeps nothing

function claimKey(user, key, target):
    try: insert (user, key, target) into idempotency_keys; return new claim
    catch uniqueViolation:                              // the unique index decides who is first
        row = find(user, key)
        if age(row) > 24 hours: delete row; try again once
        if row.target != target: fail 409 IDEMPOTENCY_KEY_REUSED
        if row.response is empty: fail 409 REQUEST_IN_PROGRESS
        return replay(row.statusCode, row.response)
\end{lstlisting}

\subsection{Өдрийн сануулга}
Өглөө бүр ажилтанд тухайн өдөр дуусах болон хоцорсон ажлын жагсаалт, менежерт багийн хоцорсон болон хариуцагчгүй ажлын жагсаалт илгээгдэнэ. Сервер UTC цагаар ажилладаг тул тооцоог байгууллагын цагийн бүсээр хийнэ. Cron цаг тутам ажиллаж, тохируулсан цагаас хойш үдээс өмнөх эхний ажиллалтаар илгээнэ. Мэдэгдлийн эх сурвалж нь тухайн өдөр тул нэг хүнд өдөрт нэгээс илүү сануулга очихгүй (idempotent).

\begin{lstlisting}[caption={Өдрийн сануулга},label={lst:remind}]
every hour:
    for org in organizations:
        tz = org.timeZone; hour = localHour(tz, now)
        if hour < REMINDER_HOUR or hour >= 12: continue
        day = localDate(tz, now)
        for person in org.activeUsers:
            due  = tasks(person) where status not in {done, backlog} and dueDate == day
            late = tasks(person) where status not in {done, backlog} and dueDate <  day
            if (due or late) and not notified(person, source = day):
                notify(person, due, late, source = day)
\end{lstlisting}

\subsection{Сарын тайлан бүрдүүлэх ба хаах}
Сарын тайлан тухайн сарын бүртгэлүүдээс (ажил, аудит, өдрийн болон цагийн бүртгэл, зардал, өдрийн зорилго, үнэлгээ) нэг функцээр тоологдоно. Сар нээлттэй байхад шууд хүснэгтүүдээс, хаагдсаны дараа хадгалсан хуулбараас тоологддог боловч дүрэм нэг тул хоёр үр дүн зөрөхгүй. Биелэлтийн хувь нь ажлын одоогийн төлвөөс бус, хэзээ дууссанаас тооцогдоно:
\begin{equation}
C = \frac{\left|\{t \in P_m : t.\mathrm{completedAt} \le \mathrm{end}(m)\}\right|}{|P_m|}
\end{equation}
энд $P_m$ -- $m$ сард төлөвлөгдсөн ажлын олонлог. Хагас жил, жилийн тайлан хаагдсан сарын тайлангуудын нийлбэр тул батлагдсан сарын тайлантай үргэлж тохирно. Хаасан сарыг зөвхөн админ шалтгаан (3--500 тэмдэгт) бичиж дахин нээх ба хэн, хэзээ, яагаад нээснийг хаасан хувилбарын хамт хадгалдаг тул тайлангийн өмнөх хувилбаруудыг одоогийн дүнтэй харьцуулж болно. Тайлангийн тойм бичвэрийг менежер хүсвэл Claude хэлний загвар ноороглоно~\cite{anthropic}; загвар руу зөвхөн нэгдсэн тоо, нэргүй саад бэрхшээл илгээгдэх ба ноорог менежер батлахаас нааш албан ёсны бичвэр болохгүй.

\subsection{Бүтээмжийн үзүүлэлт тооцох}
\label{sec:kpialgo}
Хүснэгт~\ref{table:kpi}-ийн K1--K4, K6-г сарын тайлан бүрдэх үед ажил, аудит, долоо хоногийн тайлангийн бүртгэлээс цэвэр функцээр тооцно (Эх код~\ref{lst:kpi}). Үр дүн бүр ижил хэлбэртэй: утга (value), тоологч (numerator), хуваарь (denominator), тооцооноос хасагдсан бүртгэлийн тоо (excluded). Тоолох бүртгэл байхгүй бол утга 0 биш null буюу ``өгөгдөлгүй'' болно, учир нь хэмжээгүй зүйлийг хэмжсэн 0 гэж харуулбал тайлан төөрөгдүүлнэ. Бүх огноог байгууллагын цагийн бүсээр хөрвүүлж харьцуулна; огноо нь хүчингүй бүртгэлийг (жишээ нь 2-р сарын 30) тоолохгүй, хасагдсанд тооцно. K2, K4, K6-д тоологдсон бичлэгүүдийг тайлан болон CSV-д нотолгоо болгон жагсаадаг тул тоо бүрийг эх бүртгэл хүртэл мөрдөж болно. Ажилтан өөрийн, менежер багийн бүртгэлээс тоологдсон дүнг харна. Тооцоо нь ажлын тоо $n$, аудитын тоо $m$, хүлээгдэх хүн $p$, сарын долоо хоног $w$-ээр $O(n + m + p \cdot w)$ хугацаатай.

\begin{lstlisting}[caption={Бүтээмжийн үзүүлэлт (K1--K4, K6)},label={lst:kpi}]
function monthlyMeasurements(records, month, tz, refDay):   // refDay: month end, or today
    // K1: share of the tasks finished this month that were finished on time
    done = [t in records.completed where localDate(t.completedAt, tz) in month
                                     and t.dueDate is a valid date]
    K1 = measure(count(t in done where localDate(t.completedAt, tz) <= t.dueDate), len(done))
    // K2: committed tasks that are late at the reference day
    late = [t in records.lateCandidates where t.status != backlog
            and t.dueDate < refDay and not finishedBy(t, refDay)]
    K2 = meanDays(sum(refDay - t.dueDate for t in late), len(late))
    // K3: mean score of submitted audits of a zone
    K3 = mean(a.score for a in records.audits where a.zoneId and a.submitted
                                              and 0 <= a.score <= 100)
    // K4: elapsed days from creation to completion of audit-raised fixes
    K4 = meanDays(sum(t.completedAt - t.createdAt for t in done
                      where t.sourceType == audit_run), ...)
    // K6: person-weeks with a check-in / expected person-weeks
    K6 = measure(count(written(person, week)), len(people) * len(weeksStarted(month, refDay)))
    return each as {value or null, numerator, denominator, excluded}
\end{lstlisting}

\subsection{Засварын үр дүнг шалгах (PDCA ``Шалгах'')}
\label{sec:pdcacheck}
Аудитаас үүссэн засах ажил хаагдсан нь ажил хийгдсэн гэсэн үг боловч асуудал арилсныг батлахгүй. PDCA мөчлөгийн ``Шалгах'' алхмын нотолгоо нь тухайн бүсийн дараагийн аудит юм~\cite{deming}. Алгоритм илгээсэн, оноотой аудитуудыг бүсээр бүлэглэж цагаар эрэмбэлээд, аудитаас үүссэн засвар бүрийг Зураг~\ref{fig:fixverify}-д заасан зургаан төлөвийн аль нэгэнд ангилна (Эх код~\ref{lst:pdca}). Баталгаажуулалтын хувь нь verified засварын дахин аудитлагдсан (verified, improved, not\_improved) засварт эзлэх хувь бөгөөд үзүүлэлтүүдийн адил тоологч, хуваарь, хасагдсан тоотой. Хасагдсанд үүсгэсэн аудит нь устсан болон дууссан мөч нь бүртгэгдээгүй (done\_undated) засвар орно. Төвөгшил нь аудитын тоо $r$, засварын тоо $t$, бүсийн аудитын тоо $k$-аар $O(r \log r + t \cdot k)$.

\begin{figure}[H]
\centering
\includegraphics[width=\linewidth]{Figures/fix_verification.png}
\caption{Аудитаас үүссэн засварыг дараагийн аудитаар ангилах}
\label{fig:fixverify}
\end{figure}

\begin{lstlisting}[caption={Засварын үр дүнг шалгах},label={lst:pdca}]
function verifyImprovements(tasks, runs):
    byZone = submitted runs with a score, grouped by zoneId and sorted by time
    for task in tasks where task.sourceType == audit_run:
        trigger = runs[task.sourceId]
        if task.status != done:          status = open
        else if no task.completedAt:     status = done_undated
        else:
            next = first run of byZone[trigger.zoneId] after task.completedAt
            if no next:                  status = awaiting_reaudit
            else if next.score >= 85:    status = verified
            else if next.score > trigger.score: status = improved
            else:                        status = not_improved
    rate = verified / (verified + improved + not_improved)    // null when none re-audited
\end{lstlisting}

Залруулах үйлдлийн гогцоог бүрэн болгохын тулд засварт ``үндсэн шалтгаан'' талбар нэмэв: түүнийг засвар хийсэн ажилтан эсвэл менежер бичнэ. Менежер дууссан засварыг баталгаажуулна (fixes:signoff эрх); дуусаагүй засварыг (FIX\_NOT\_DONE) болон өөрийнхөө хийсэн засварыг баталгаажуулахыг татгалзана, засварыг дахин нээвэл баталгаажуулалт цуцлагдана. Үндсэн шалтгаан, баталгаажуулалт нь баталгаажуулалтын хувийг өөрчлөхгүй: засвар ажилласан эсэхийг зөвхөн дараагийн аудит шийднэ.

\subsection{Нууц үг сэргээх ба session дуусгах}
Нууц үг сэргээх токены зөвхөн hash-ийг хадгалж, токеныг нэг удаа, нөхцөлтэй UPDATE-ээр атомаар хэрэглэнэ: токен хэвээр, хугацаа нь дуусаагүй мөрийг л шинэчилдэг тул нэг токентой зэрэг ирсэн хоёр хүсэлтээс нэг л амжина (Эх код~\ref{lst:reset}). ``Нууц үгээ мартсан'' хүсэлтэд бүртгэлтэй, бүртгэлгүй, идэвхгүй хаягт ижил хариуг мэйл илгээхээс өмнө буцаадаг тул хариуны агуулга, хугацаагаар бүртгэл байгаа эсэхийг тандах боломжгүй. Хэрэглэгч бүр token\_version-тэй; refresh токен үүсэхдээ тухайн хувилбарыг агуулах ба нууц үг солих эсвэл сэргээхэд хувилбар нэмэгдэж өмнөх бүх refresh токен хүчингүй болно~\cite{jwt}. Нууц үгээ сольсон төхөөрөмж хариундаа шинэ session авна. Вэб refresh токеныг HttpOnly, SameSite=Strict cookie-д хадгалдаг тул хөтөч дээрх script уншиж чадахгүй.

\begin{lstlisting}[caption={Сэргээх токеныг атомаар хэрэглэх},label={lst:reset}]
function completePasswordReset(userId, tokenHash, newPassword):
    affected = UPDATE users
               SET password = bcrypt(newPassword), resetToken = null,
                   resetExpires = null, tokenVersion = tokenVersion + 1
               WHERE id = userId and resetToken = tokenHash and resetExpires > now()
    return affected == 1               // of two concurrent requests only one wins

function refresh(token):
    if token.version != user.tokenVersion: fail 401 AUTH_SESSION_EXPIRED
\end{lstlisting}

Ажилтны ажлын жагсаалт ``хоцорсон $\rightarrow$ өнөөдөр $\rightarrow$ энэ долоо хоног $\rightarrow$ дараа $\rightarrow$ хугацаагүй $\rightarrow$ дууссан'' дарааллаар бүлэглэгдэнэ. Хэн ч амлаагүй (backlog) ажил хоцордоггүй. Алгоритм нэг дамжилтаар $O(n)$ хугацаанд ажиллана.

export const scoreAnswers = (
  template: Pick<AuditTemplate, 'questions'> | undefined,
  answers: AuditAnswers,
): number => {
  if (!template) return 0;

  let earned = 0;
  let possible = 0;

  template.questions.forEach((question) => {
    if (question.type === 'score') {
      possible += question.maxScore || DEFAULT_MAX_SCORE;
      earned += Number(answers[question.id] || 0);
    }

    if (question.type === 'yes_no') {
      possible += 1;
      earned += answers[question.id] === 'yes' ? 1 : 0;
    }
  });

  return possible ? Math.round((earned / possible) * 100) : 0;
};
\end{lstlisting}

\subsection{Аюулгүй байдал ба найдвартай байдлын тест}

\subsection{Хэмжилтээр олдсон гацаа ба засвар}
\label{sec:bottleneck}
Эхний хэмжилтээр сарын тайлангийн p95 1\,753 мс, хамгийн удаан нь 2\,304 мс байсан нь NFR-06-ийн босгод ойртож, заримдаа давж байв. Алгоритмыг тусад нь хэмжихэд K1, K3-ын тооцоо 10\,000 бүртгэлд 1\,278 мс зарцуулж байсан. Шалтгаан нь огноог байгууллагын цагийн бүсээр хөрвүүлдэг dayIn() функц дуудагдах бүртээ шинэ Intl.DateTimeFormat объект үүсгэдэг байсан явдал: алгоритм $O(n)$ хэвээр боловч нэг алхмын өртөг өндөр байв. Formatter-ийг цагийн бүс бүрт нэг удаа үүсгэж кэшлэхэд (Эх код~\ref{lst:daycache}) ижил өгөгдөл дээр сарын тайлан 9 дахин, тооцоо 69 дахин хурдассан (Хүснэгт~\ref{table:beforeafter}, Зураг~\ref{fig:beforeafter}). Бусад endpoint-ийн хугацаа хэмжилтийн хэлбэлзлийн хүрээнд үлдсэн.

\begin{lstlisting}[caption={Огнооны formatter-ийг цагийн бүсээр кэшлэх},label={lst:daycache}]
const dayFormatters = new Map<string, Intl.DateTimeFormat>();

export const dayIn = (timeZone: string, moment: Date) => {
  let formatter = dayFormatters.get(timeZone);
  if (!formatter) {
    formatter = new Intl.DateTimeFormat('en-CA', { timeZone, year: 'numeric', month: '2-digit', day: '2-digit' });
    dayFormatters.set(timeZone, formatter);
  }
  return formatter.format(moment);
};
\end{lstlisting}

\section*{Бүлгийн дүгнэлт}
Энэ бүлэгт системийн давхаргат архитектур, зохиомжийн класс, дарааллын диаграмм, өгөгдлийн сангийн схем, эрхийн загварыг боловсруулав. Аудитын оноо ба засах ажил, сүлжээгүй горимын дараалал, давхар бичилтээс сэргийлэх Idempotency-Key, өдрийн сануулга, сарын тайлан, бүтээмжийн үзүүлэлт, засварын үр дүнг шалгах PDCA алхам, нууц үг сэргээх, ажлын бүлэглэлт гэсэн алгоритмуудыг зохиомжилж хэрэгжүүлэв. Системийг зургаан түвшинд 2\,360 автомат тестээр шалгаж, 22 use-case бүгд хүлээн авах тестээ давсан. Гүйцэтгэлийн хэмжилтээр сарын тайлангийн гацааг илрүүлж 9 дахин хурдасгасан бөгөөд бүх endpoint NFR-06-ийг хангасан. ISO/IEC 25010-ын долоон шинж чанараас дөрөв нь бүрэн хэмжигдсэн, ашиглахад хялбар байдал, найдвартай байдал, нийцтэй байдлын үлдсэн хэсгийг туршилтын ажиллагаанд хэмжинэ.
